# Wayfinder: Antigravity ACP file-policy boundary

Research decision for [#60](https://github.com/Riso-application-factory/zed-ai-crew/issues/60), retrieved **2026-10-15 UTC** (official web pages inspected approximately 03:36–03:41 UTC; pinned SDK source refreshed at 03:41:52 UTC). This is public documentation/source research; no new agent execution or policy configuration was tested.

**Decision: a supported exclusion for the installed ACP1.3.0 route is not established.** Google documents plausible controls for other consumers, especially a `PreToolUse` hook that can deny `view_file`, but the inspected sources do not establish that this pinned ACP adapter loads those controls, applies them to its exposed file route, or preserves ACP/MCP when doing so. This is an unresolved version/consumer contract, not evidence that every supported solution is impossible.

## Actual baseline and version boundary

The [retained report](../evidence/wayfinder/confinement/antigravity-native-file-report.md) and [#18 evidence comment](https://github.com/Riso-application-factory/zed-ai-crew/issues/18#issuecomment-6183819288) record three runs/six epochs: ACP-exposed `view_file` returns a synthetic isolated app-state canary outside the worktree; the same path through the confined MCP effect receives OS EPERM. A nonstate path gets a model-visible application denial but ACP reports completed without error content. Complete k3 wire contains no client `fs/*` or `terminal/*` callback for those reads. This establishes a route-level counterexample, not exclusive attribution of the file syscall to a native process.

The [pinned registry record](https://github.com/agentclientprotocol/registry/blob/f6c0f4e8357c7f28e84e3b883695c387b04ed2b9/antigravity-acp/agent.json) identifies Google LLC, proprietary licensing, version **1.3.0**, binary archives hosted on `dl.google.com`, and `agy_acp_server.par` on macOS/Linux. That record supplies distribution commands, not a file-policy schema or public adapter implementation. The installed pair remains pinned; nothing here proposes an upgrade.

## Pinned SDK source does not establish an ACP consumer

Public SDK commit `f61cb2fa54a0a3c46dac690f32e4346995662297` distinguishes removing tools from model exposure from runtime policy denial ([types.py](https://github.com/google-antigravity/antigravity-sdk-python/blob/f61cb2fa54a0a3c46dac690f32e4346995662297/google/antigravity/types.py#L641)). Its [connection.py](https://github.com/google-antigravity/antigravity-sdk-python/blob/f61cb2fa54a0a3c46dac690f32e4346995662297/google/antigravity/connections/connection.py#L43) resolves an allowlist or defaults minus disabled tools. The local connection serializes policy configuration and registered pre-tool hooks ([local_connection.py](https://github.com/google-antigravity/antigravity-sdk-python/blob/f61cb2fa54a0a3c46dac690f32e4346995662297/google/antigravity/connections/local/local_connection.py#L1374)). These establish SDK ownership/transport, not ACP input consumption.

SDK policy precedence is specificity first: specific deny/ask/allow groups precede wildcard deny/ask/allow groups; first match wins within a group ([policy.py](https://github.com/google-antigravity/antigravity-sdk-python/blob/f61cb2fa54a0a3c46dac690f32e4346995662297/google/antigravity/hooks/policy.py#L19)). Do not substitute the app/CLI resource-list precedence for this algorithm. Refetched source fingerprints are in the [source index](../evidence/wayfinder/confinement/antigravity-acp-file-policy-archive/sdk-source-index.json); SDK commit identity is not an ACP binary build identity.

## Hook candidate and precedence limits

The [hook contract](https://antigravity.google/docs/hooks/) registers named event configurations in `.agents/hooks.json` or `~/.gemini/config/hooks.json` for its documented consumers. A `PreToolUse` handler receives the proposed call before execution; `deny` stops it, `allow` continues to another hook/default policy, and `auto_approve` still honors explicit rules. A handler restricted to `view_file` could reject app-state paths while leaving MCP outside that matcher. **This is a design inference, not an executed or version-supported ACP fix.** The page does not establish ACP hook loading, source-merge order, failure/timeout posture, or the ordering of adapter tools versus native hooks. Path aliases in the measured adapter schema also require an established normalization contract; a name match alone is insufficient.

The current [agent-settings page](https://www.antigravity.google/docs/agent-settings#agent-non-workspace-file-access) places the project-plus-local-app-data default under **Windows**. Its current macOS/Linux section describes app permission presets. Neither section establishes the installed macOS ACP1.3.0 behavior. The [changelog](https://antigravity.google/docs/changelog/) separates product surfaces; its `v1.3.0` CLI/extension entries must not be equated with ACP1.3.0 merely by version number.

## Bounded search and exact blocker

Inspected primary sources: the URLs linked above; Google's [IDE extensions overview](https://antigravity.google/docs/ide/extensions/); the public [CLI repository listing](https://github.com/google-antigravity/antigravity-cli), which exposes documentation/examples but did not establish ACP implementation source; and the pinned registry record. Searched current Google pages/changelog for ACP, hooks, settings and version linkage, plus targeted searches for `site:antigravity.google "ACP" hooks`, `site:antigravity.google "agy_acp_server" settings policy hooks`, and `site:github.com/google-antigravity "acp" "hooks.json"`. No supported ACP file-exclusion schema/source/release mapping emerged from that scope. Third-party patches, decompiled snippets, community reports, arbitrary newer archive URLs and runtime probes were not evidence for this conclusion.

The exact blocker is a first-party, version-applicable contract or public source showing **which ACP1.3.0 input is consumed, by which component, before the measured `view_file` dispatch, with what precedence and errors**, and that the same configuration retains ACP plus the existing MCP flow. A published SDK API, current app/CLI guide, binary distribution manifest, or ACP progress notification alone does not supply that contract.

The smallest next investigation is a bounded applicability prototype of the documented project hook file in a disposable worktree, against unchanged ACP1.3.0. This tests a consumer/version hypothesis; it does not establish a supported ACP contract in advance. Use one absolute owned command path and invocation receipts to distinguish actual hook loading from a configuration file merely existing. Match the hook input and decision to the exact file attempt and model result. Preserve the same synthetic app-state/worktree controls, MCP positives/same-path EPERM and independent custody. If no hook invocation is observed, stop with that specific loading gap; do not sweep undocumented keys, environment variables or additional settings locations.

Hook execution alone is not proof of denial. A successful first comparison would still leave hook-load failure, timeout, alternate path arguments, resume and fail-closed behavior unverified. No such runtime verification was run in this research. The bounded research question is answered by the precisely unlocated ACP mapping and the named candidate; #18 and the destination remain unresolved. Published resolution and successor tracker links are recorded separately after real records exist.
