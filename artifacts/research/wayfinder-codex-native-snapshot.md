# Native Codex policy / effective-config snapshot contract

Status: **source audit complete; native execution and architecture choice not performed by this audit**. Canonical decision: [#28](https://github.com/Riso-application-factory/zed-ai-crew/issues/28). Return point: [Confinement #18](https://github.com/Riso-application-factory/zed-ai-crew/issues/18). Research inspected the public `rust-v0.160.1` source under `/private/tmp/codex-rust-v0.160.1/codex-rs` and installed ACP 2.2.2. Matching the source release version is not binary-to-source attestation. No real preference values, account credentials or private config were read for this audit.

## Result

The pinned stock app-server exposes useful native configuration reads, but **neither read is an authoritative, complete, atomic snapshot of the configuration and authority of a particular thread/request before tool dispatch**. They lack a common generation, omit managed source attribution and several classes of requirements, and cannot accept the session/request overrides that thread creation materializes. Combining them, or treating executor projections as an alternative, does not close that gap. This conclusion is bounded to the reviewed pinned contracts; it is not a claim that a bridge cannot be developed.

Public Rust library entry points allow a real native loader fixture with **nonempty synthetic managed requirements** and relocated public config sources. They can test native parsing, composition, source attribution and explicit reload/errors without querying host MDM. These are test/embedding knobs, not a stock CLI snapshot injection API or proof that the actual native ACP control plane has been admitted. An embedder would still need to create and enforce its own whole-context admission boundary and maintain compatibility with this source pin.

Both config reads use `global_shared_read("config")` serialization scopes. That coordinates relevant RPC scheduling, but does not make two RPCs one transaction, bind a read to a later tool dispatch, or prevent external file/MDM changes. The protocol provides no combined config-and-requirements read. [Scopes](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server-protocol/src/protocol/common.rs#L1399).

`layers[].version` is a SHA-256 fingerprint of canonical TOML content; it is not a monotonic load generation, full dependency set, trust proof or policy freshness lease. Config layers track requirements sources separately. Requirements response has no layer versions at all. [Fingerprint](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/fingerprint.rs#L62), [layer accessors](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/state.rs#L493), [requirements response](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server-protocol/src/protocol/v2/config.rs#L737).

`requirements: null` means the successfully loaded native requirements object was empty under that endpoint's rules and running auth mapping. It is not independently usable proof that a denied preference read represented no MDM policy, that all requirement sources were trusted/current, or that a later thread's context has no managed restrictions. Real load errors propagate from the service; the denied/empty projection concern remains separate. [Read behavior](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/config_manager_service.rs#L179), [null mapping](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/request_processors/config_processor.rs#L391).

## Internal native loading and context

Native `load_config_layers_state` composes system → cloud → legacy → MDM requirements, while ordinary config layers use package → admin → system → cloud → user → selected profile → project → runtime. Untrusted project layers are loaded but disabled. Project-local configuration has a denylist for credential destinations, provider configuration, legacy notify and other fields. Trust/context must therefore be part of an admission input, not inferred from the final few keys. [Ordering and public loader](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/mod.rs#L84), [requirements composition](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/managed_requirements.rs#L69).

`ConfigManager::load_with_cli_overrides` refreshes application policy first, combines base CLI flags with request overrides afterward, builds full native config with typed harness overrides, cwd and thread loader, then checks the captured application policy load. Thus a prior base config read cannot attest later request overrides. The retained-session paths rebuild current global/managed settings with previous session layers; they are separate from a thread-agnostic read. [Builder path](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/config_manager.rs#L428), [retained session](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/config_manager.rs#L213).

The internal typed `ConfigLayerStack::requirements()` retains `Sourced<T>` values and constraints. `RequirementSource` includes system file, enterprise fragment ID/name, MDM domain/key and composite sources. This is stronger diagnostic provenance than the stock RPC exposes, but synthetic overrides receive the same MDM source tag as actual MDM: **that tag is not authenticated provenance**. A Crew fixture/bridge must retain its own synthetic/source label and never call it an observed host policy. [Source types](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/config_requirements.rs#L44), [Sourced](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/config_requirements.rs#L1120), [override labeling](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/macos.rs#L96).

`ConfigLayerStack::effective_config()` merges active ordinary layers and required provider definitions. It does **not** itself materialize all native constrained effective settings or runtime feature defaults. A config-crate-only fixture must compare ordinary layered values with typed requirements rather than present its TOML as a full engine snapshot. [Implementation](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/state.rs#L475), [RPC materialization](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/config_manager_service.rs#L137).

## Native freshness and revocation

The app-server has a genuine native application-network lifecycle: reloads serialize through a semaphore, load local policy before cloud access, capture cloud inputs and publish into the current revision. Each ConfigManager load checks both network revision and **private Arc snapshot identity** after native config building. Changed policy/cloud inputs replace that identity; unchanged inputs may reuse it. Errors clear the snapshot and make policy unavailable. This is real internal stale-load protection, not an external whole-config snapshot API. The snapshot tracks application destination policy and cloud bundle, not a complete atomic snapshot of all user/project/MDM/thread inputs. [Lifecycle](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/application_network.rs#L68), [private fields](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/config_manager.rs#L59).

`NetworkPolicyRevision` identifies the account/configuration publication generation. A successful publish does not increment it. Publishing a changed policy revokes disallowed outstanding permits and signals change watchers; `unavailable` revokes current permits without changing account; `invalidate` increments revision/account, marks unavailable and revokes all permits. Consequently **revision alone cannot detect every effective change**. These controls cover attached application transports and destination permits, not filesystem/process/FD rights or all tool dispatch. [Controller](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/http-client/src/network_policy.rs#L139), [invalidate/acquire](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/http-client/src/network_policy.rs#L245).

Existing native tests describe malformed-policy reload denial, stale snapshot rejection, serialized concurrent loads and a cloud config change that supersedes a snapshot even when network rules are unchanged. They have **not been executed by this source audit**. They are useful candidate runtime checks, not verified results. [Reload/error test](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/application_network_tests.rs#L83), [concurrent reload test](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/application_network_tests.rs#L169), [cloud-only change](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/application_network_tests.rs#L251), [small native permit tests](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/http-client/src/network_policy_tests.rs#L39).

Turn entry refreshes current application policy and validates retained provider selection/definitions before accepting a turn. This is not evidence of a continuous MDM watch, instant revocation of all generated operations, or a snapshot lease checked before every tool dispatch. [Turn entry](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/request_processors/turn_processor.rs#L538), [provider check](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/config_manager.rs#L261).

## Smallest honest public native fixture

The proposed fixture is a new throwaway Rust example or integration test against the pinned **unmodified native config crate**. It should use a read-only public-fixture `ExecutorFileSystem` implementation, based on the native test filesystem, returning explicit errors for unsupported operations. `codex_exec_server::LOCAL_FS` is also public but adds the heavier exec-server dependency. This fixture does not start the installed native executable, an ACP session or a production engine. [Native test filesystem](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/tests.rs#L319), [host filesystem](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/exec-server/src/local_file_system.rs#L54).

Use public `LoaderOverrides` with relocated absolute packaged/system/user/legacy/requirements paths and **both** nonempty `managed_preferences_base64` and nonempty `macos_managed_config_requirements_base64`. Keep `ignore_managed_requirements=false`; do not use an empty snapshot to claim policy absence. All inputs must be synthetic and label that origin separately from native diagnostic MDM tags. Nonempty explicit requirement override skips real CF synchronization in `load_local_application_requirements`, and both explicit overrides avoid real managed preference value reads in their respective loaders. [Knobs](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/state.rs#L43), [application sync condition](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/application.rs#L43), [requirements parse](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/macos.rs#L96), [ordinary managed layer](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/loader/layer_io.rs#L121).

Concrete public inputs and checks (proposed; execution belongs in the #28 probe record):

1. Nonempty managed defaults: `model = 'crew-public-mdm-default'`. Nonempty managed requirements: `[features] hooks = true; memories = false` encoded from actual multiline TOML, plus `[application.network.domains] 'crew-public.example' = 'allow'`. This exercises authoritative pins without executing command hooks. Use canonical `memories`, not legacy managed `memory_tool`.
2. Relocated system/user/project files with distinct public model values; public `.project-root` and selected trust entry. Call `load_config_layers_state` with explicit cwd/CLI values, strict config and a `NoopThreadConfigLoader`; inspect active/disabled layers, origin versions, raw merged values, typed requirements and their sources. Repeat with untrusted project to measure disabled-layer semantics.
3. Add a synthetic cloud fragment through the native test-support bundle loader and inspect precedence against the MDM requirements. This is simulated cloud input with native composition, not evidence of an enterprise account or network fetch. [Fixture loader](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/test_support.rs#L14).
4. Mutate a public system requirement file after the first native load, reload and show the native parsed value/source changed. Introduce malformed requirements and observe an error. Reject stale output in the proposed bridge; do not call a retained owned hash native revocation.
5. Exercise actual native `NetworkPolicyController` separately: initial unavailable, publish restricted policy, acquire allowed positive permit, tighten/remove destination, prove retained permit revocation, failed-load unavailability and invalidated-generation publication rejection. Label this native policy primitive behavior; it is not an app-server loader or actual ACP dispatch binding.

This can answer native loader and transport primitive feasibility. It cannot by itself satisfy #28's entire privileged startup/tool-boundary criterion or choose a production topology. Actual generated execution deny controls remain evidence from separate executor probes until the native control plane is bound to that executor.

An embedding cannot claim that prebuilding one Config freezes the authoritative context. [Load/activate](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/in_process_bootstrap.rs#L21), [configure](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/app-server/src/in_process_bootstrap.rs#L101).

That does not supply a missing snapshot generation or a dispatch authority lease.
