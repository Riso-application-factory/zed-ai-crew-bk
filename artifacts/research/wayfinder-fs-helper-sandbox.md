## Destination and entry evidence

The [canonical #33 result](https://github.com/Riso-application-factory/zed-ai-crew/issues/33#issuecomment-6139161784) records an owner-admitted non-null filesystem sandbox allowed-write request failing with exit 71 and `sandbox-exec: sandbox_apply: Operation not permitted`; read-only fails identically. Same-receiver sandbox=null write and actual ACP/native patch succeed. These are prior executed observations, not rerun or independently measured by this researcher. The read-only error does not validate helper policy without an allowed positive.

[ADR 0001](../../docs/adr/0001-hybrid-orchestration.md) preserves the accepted boundary: LLM interprets; code owns valid execution/state/permissions. A broader launcher or application-level access check must therefore be explicit and testable, never inferred from model cooperation. ## Primary facts and smallest seam

The public Apple SDK header at `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/usr/include/sandbox.h`, lines 23–27, states that when a process is already sandboxed the new profile is ignored and sandbox initialization returns an error. Its declarations label `sandbox_init` **“No longer supported”**, and the header recommends App Sandbox instead. This is directly read local Apple-distributed source, not a third-party paraphrase or a claim about private sandbox SPI. SDK header bytes/hash appear below. The documented public API therefore supplies no supported second initialization mechanism for this already confined child.

Pinned Codex `rust-v0.160.1` correctly prepares a filesystem-specific helper command, not an accidental ordinary exec-server startup. `FileSystemSandboxRunner::sandbox_command` validates native paths, materializes roots, adds runtime read permissions and uses restricted networking. `sandbox_exec_request` selects enforcement and rejects `SandboxType::None` with `filesystem sandbox cannot be enforced on this executor`; its command is `codex_self_exe --codex-run-as-fs-helper`. [Native runner, lines 95–200](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/exec-server/src/fs_sandbox.rs#L95-L200).

The macOS transform builds an inline Seatbelt profile and command arguments `-p`, full policy, parameters, `--`, helper command. The executable is explicitly `/usr/bin/sandbox-exec`. [Executable pin, lines 58–62](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/sandboxing/src/seatbelt.rs#L58-L62), [policy/arguments, lines 1045–1109](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/sandboxing/src/seatbelt.rs#L1045-L1109). The native base policy documents child inheritance, allows fork/exec and starts deny-default. [Base profile](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/sandboxing/src/seatbelt_base_policy.sbpl#L8-L15).

The selected #33 fixture already handles the exact helper argument synchronously before its ordinary Tokio runtime (`crew_receiver_fixture.rs:179–184` in the fingerprinted snapshot). Upstream arg0 dispatch similarly handles it. [Upstream dispatch](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/arg0/src/lib.rs#L104-L114). The helper payload selects individual filesystem operations and the child executes them with the direct filesystem implementation inside the sandbox applied by its launcher. [Helper protocol/entry implementation](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/exec-server/src/fs_helper.rs). Fixing argument dispatch again, switching the helper’s Tokio entrypoint, or adding a pathname read grant would not remove that second sandbox initialization. This is an inference from the command construction and prior error, not a fresh runtime conclusion.

The helper is spawned directly by the filesystem runner, outside process-start admission. The runner sends its payload and waits for helper output; failure preserves exit status/stderr. Spawn uses explicit descriptor policy and no fork fallback. [IO/wait and spawn, lines 392–551](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/exec-server/src/fs_sandbox.rs#L392-L551). The earlier [guard lifetime audit](wayfinder-fs-admission-guard.md) remains applicable: any redirected launch must retain the same receiving owner guard until effect/helper completion, including cancellation and transport failure. It must not introduce process-global grant reuse or treat launch acceptance as completed mutation.

## Supported Apple direction versus profile hypotheses

Apple’s App Sandbox documentation describes child sandbox inheritance through `posix_spawn`/`NSTask` and specifies the two child entitlement keys `com.apple.security.app-sandbox` and `com.apple.security.inherit`. It recommends XPC for privilege separation; inheritance supplies static parent rights, not a new per-request narrower profile. These are signed App Sandbox arrangements, not a documented allow rule for reinitializing the current custom Seatbelt fixture. Changing signing or entitlements would require a separately shaped topology. [Apple inheritance documentation](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html#//apple_ref/doc/uid/TP40011195-CH4-SW3).

Apple documents XPC services as separately sandboxed, launched/managed by `launchd`, and intended for privilege separation. The connection is independent of a live service instance; crashes invalidate it, and services can terminate abruptly. That supports separating narrowly bounded components rather than attempting an inherited sandbox reinitialization. It does not prove a Crew XPC implementation, exact request identities, policy publication, cancellation or compatible helper process lifecycle. [Apple Creating XPC Services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingXPCServices.html).

No primary source consulted supplies a supported SBPL `allow` operation that turns forbidden reinitialization into safe stacked policies. Absence in this bounded research is not proof that all private mechanisms or OS versions are impossible. Do not promote an undocumented `forbidden-sandbox-reinit` allow string, ordinary file grant, entitlement guess or `allow default` profile into a supported remedy. The parent’s actual native-helper repro should distinguish setup failure from filesystem capability denial.

## Alternatives and authority trade-off

| Proposed alternative | What it resolves | What it retains / changes | Required evidence before calling it feasible |
| --- | --- | --- | --- |
| Keep topology; fix only helper argument/runtime | Entrypoint defects if any | Existing outer boundary unchanged; still attempts second sandbox initialization | Current source already has entry dispatch. A distinct demonstrated defect would be needed; no evidence here makes this the reinitialization remedy. |
| Keep receiver outer sandbox; run helper inheriting it with explicit request policy validation | Avoids second initialization | Retains outer kernel ceiling and receiver grant, but request-specific narrower/read-only guarantees move into trusted code instead of an independently enforced helper sandbox | Every supported request path/options/symlink/alias/rename/copy must obey an explicit contract; actual read-only deny and write positive. This is a changed enforcement model, not a transparent source fix or current native helper guarantee. |
| Narrow additional public outer profile rule | Might repair an ordinary launch/read capability failure | Could retain boundaries if exact permitted capability is known | No supported reinit rule identified. Need an actual native allowed positive and paired controls; adding file permissions cannot be assumed to repair initialization. A broad profile alone is not evidence of safe stacking. |
| External restricted launch authority; helper starts once with bounded combined policy | Avoids inherited reinitialization and can retain native helper operation/response | Receiver stays confined; trusted launcher receives only admitted operation and owns helper launch outside receiver ancestry. New privileged-in-topology component must be bounded, authenticated and prevented from widening authority | Exact launcher interface, startup authority, request/profile/attempt binding, guard lifetime to child completion, real helper allow/deny, malformed/replayed requests and outside/process/network/credential controls. Unsandboxed-parent launch separation is a proposal, not an accepted production service. |
| Signed independently sandboxed XPC service | Uses Apple-documented privilege separation instead of custom nesting | Changes packaging/signing/service identity and lifecycle; static entitlements alone do not supply dynamic native request scope | Real service packaging, caller identity, capability/transport boundaries, matching FS semantics and completion/cancel evidence. Larger than a source-only adapter. |
| Remove receiver outer confinement or bypass requested sandbox | Can make helper initialize or direct writes work | Loses the proven receiver ceiling, or silently drops request restrictions | Outside scope without explicit Human decision; not recommended as a hidden feasibility fallback. |

A helper launched by external authority must start with the intersection of admitted request rights and the outer security ceiling. **Do not assume concatenating SBPL allow sections computes that intersection.** This is a design requirement/inference: escaping parent ancestry discards inherited enforcement, so filesystem roots, process execution, network targets, credential paths and descriptor/environment rules must be deliberately reconstructed and verified. Preserve the owner guard across the IPC round trip and helper wait. A helper that can inherit arbitrary host descriptors or execute caller-selected programs is a materially broader authority than the current fixed native filesystem helper.

The smallest useful next investigation is the parent’s exact-helper positive/deny experiment with an explicitly restricted one-time launch outside already sandboxed receiver ancestry, compared with unchanged direct-path and outer-boundary controls. It may establish bounded feasibility while leaving production topology/authority unchosen. If no bounded candidate retains those boundaries, the actual Human question is whether to accept an external limited launcher/XPC component or adopt outer-only enforcement with explicitly narrower supported filesystem semantics. It is not a request to reconfirm A or to grant more host access generically.
