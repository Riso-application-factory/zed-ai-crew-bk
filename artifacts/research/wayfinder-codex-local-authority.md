## Decision evidence

The stock candidate “select a remote default executor and disable ordinary hooks” is insufficient. Several model-reachable paths retain host authority, and the installed ACP adapter can introduce a local MCP server without explicitly selecting its environment. A restricted effective configuration might be feasible, but its admission, immutability, managed requirements, and runtime binding remain to be proved.

The strongest concrete counterexample is ACP-supplied stdio MCP: installed `createMcpSeverConfig` constructs command/args/env without `environment_id`; the native config parser defaults this field to `local`. The MCP runtime then chooses its local launcher independently of the thread's selected executor. This is a source-supported local route, not a demonstrated exploit or a runtime observation. Installed bundle lines `35330–35341`, `35437–35492`, `35521–35542`; pinned [default](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/mcp_types.rs#L557), [launcher selection](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/codex-mcp/src/rmcp_client.rs#L1230).

## Configuration and inherited authority

Key clarification from the admission continuation: `features.memories` is the canonical key for `Feature::MemoryTool`; `features.memory_tool` is a supported legacy configuration alias. Managed feature requirements use canonical lookup, so that legacy spelling cannot be assumed to pin a managed requirement. The inventory's legacy configuration spelling above does not establish such a pin. [Canonical key](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/features/src/lib.rs#L1159), [alias](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/features/src/legacy.rs#L38), [managed lookup](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/core/src/config/managed_features.rs#L238).

ManagedFeatures normalizes and validates pinned feature requirements during construction and mutation. Explicit conflicting config values are rejected. Unknown requirement keys are ignored with warnings, so spelling is material. Managed hooks are enabled independently of ordinary per-hook enabled state; hook requirement layers append events and fail closed on conflicting active-platform directories. Disabling mandatory hooks/features to make a synthetic route pass would not preserve the actual authority requirement. Sources: [feature constraints](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/core/src/config/managed_features.rs#L43), [explicit conflict](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/core/src/config/managed_features.rs#L302), [hook composition](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/config/src/requirements_layers/hooks.rs#L75).

`NON_INHERITABLE_ENV_VARS` contains five reserved identity variables. Local hooks, code-mode host, MCP launch and executor transport have distinct environment semantics; none of that list is an arbitrary Human PAT allowlist. Shell policy supports all/none/core, excludes and overrides, then removes reserved identities. It must not replace clean launcher environment, closed FDs, or independent same-UID process-info denial. The remote unified-exec FD rejection is narrower than a proof that all launchers close every FD. Sources: [reserved variables and environment composition](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/protocol/src/shell_environment.rs#L14), [local MCP descriptor contract](https://github.com/openai/codex/blob/rust-v0.160.1/codex-rs/rmcp-client/src/stdio_server_launcher.rs#L1).

Conditional admission work therefore needs effective-config/request ownership, rather than only model-visible tool names: no unowned notify/hook commands; explicit owned MCP environment; requested MCP additions/config overrides revalidated; selected environment set excludes local; frozen host skill/plugin resources; controlled code-mode host if exposed; application API egress separate from executor egress; required features/hooks preserved or affected route rejected. These are proposed checks, not an accepted architecture or demonstrated stock configuration. A launcher-level executable allowlist or custom embedding would be another candidate, requiring proof of positive native behavior and deny behavior; neither is accepted here.

It does not exhaust hooks, memory, code-mode, host integrations or AGY authority.
