# Antigravity native history, continuation and restoration interfaces

Research date: 2026-10-14 (UTC+7). Canonical question: [confinement #18](https://github.com/Riso-application-factory/zed-ai-crew/issues/18). Read-only source research; no runtime experiment, tracker mutation, inference, authentication, profile change, proprietary extraction or binary modification in this note's research session.

**Finding:** The pinned public local SDK supports selecting persisted conversations and receiving historical steps. It does not expose a documented operation that replaces an already stored native `run_command` result. `initial_trajectory` is a protobuf initialization field, but the inspected public Python strategy neither accepts nor populates it, and the inspected sources do not define its byte serialization or replacement semantics. ACP load/resume can test continuity through the installed adapter; their success cannot establish that gateway-repaired results have become native history.

## Installed ACP-facing contract and current evidence

The installed TD1 handshake actually identifies antigravity-acp **1.3.0**, protocolVersion1, advertises loadSession:true and sessionCapabilities.list/resume. Its restart fixture calls `session/load` with sessionId/cwd/mcpServers, receives replayed user and agent text before its response, then calls `session/resume` and receives configuration without conversation replay. This proves that simple conversation path for the measured adapter, not repaired-tool persistence: [handshake JSONL:3](../evidence/technical-discovery/td1/antigravity-1-handshake.jsonl), [restart JSONL:3–13](../evidence/technical-discovery/td1/antigravity-3-restart-load.jsonl). Those earlier transcripts are evidence only; this research did not run their authentication path.

Current [ACP session setup](https://agentclientprotocol.com/protocol/v1/session-setup) requires capability checks. Both load/resume take sessionId, cwd and MCP server configuration; load replays conversation updates, resume restores context without replay. These lifecycle calls contain no native functionResponse/trajectory replacement field. ACP `session/update` is the agent's notification stream, not a client history setter. Mode/model/config setters concern configuration rather than past tool execution. Do not add speculative `session/set_history`, `trajectory/update`, undocumented metadata fields or late tool-result injection to a compatibility claim.

#47 establishes two different facts: native retains its command rejection; the owned HTTP gateway changes the outgoing model-request `functionResponse.response` to a nonce-bound helper receipt. The mutation is explicit in [antigravity-command-correlation-probe.py:137–159](../evidence/wayfinder/confinement/antigravity-command-correlation-probe.py), with model HTTP acknowledgment tracked at lines160–166. Its [report](../evidence/wayfinder/confinement/antigravity-command-correlation-report.md) excludes native compaction/internal subagents and real model comprehension. #48 preserves those bounded results through a surviving supervisor and uses fresh ACP conversations after quiescence; its [report](../evidence/wayfinder/confinement/antigravity-command-survivor-report.md) leaves provider restoration and durable supervisor recovery unresolved. Neither proves a new process has the historical nonce registry, receipt or original gateway transformation available.

## Next supported public experiments

1. **Same-session ACP restart, without history edits.** Use unchanged ACP 1.3.0 with an isolated public GEMINI_HOME and existing synthetic HTTP model/gateway fixtures. Perform one #47-style fixed fork-free helper call, retain its actual ACP sessionId and scoped nonce/receipt observations, retire/reap the first registered graph, then initialize a fresh graph against the same public storage/worktree. Exercise advertised session/load and session/resume separately with the recorded ID and explicit MCP list. Record replayed tool status/content, the first continued model request's original native functionResponse, the forwarded model request and helper effect count. Preserve current epoch fencing: historical serialization must not authorize another helper execution. Start with observational gateway handling so a stale registry rejection is not mislabeled as provider restoration failure. No real inference is needed.
2. **Raw native continuation controls.** Through the already exercised public native transport, use InputConfig.storageDirectory plus InitializeConversationEvent.config.cascadeId and sessionContinuationMode. Compare CREATE_ONLY(existing), RESUME(existing), RESUME(missing), CREATE_OR_RESUME(missing), and restart with unchanged public storage. Capture raw InitializeConversationResponse.cascadeId/history and continued synthetic model contents. Runtime rejection/ignored modes are a version compatibility result, not grounds to patch binaries. Explicit IDs and storage avoid confusing a fresh context with successful restore.
3. **In-flight callback control.** For an emitted public custom ToolCall, respond once using the supported ToolResponse ID/result fields; inspect subsequent synthetic model functionResponse and restart history. This can establish a native result path for a client-executed custom tool. It does not automatically redirect harness-side run_command or repair an already terminal rejection.

Do **not** invent an `initial_trajectory` payload format or edit conversation files to make a restore pass. A future seed/import experiment requires a first-party encoding contract or a demonstrated supported producer of those bytes. Current evidence supports a precise question: does installed same-session load/resume preserve the native rejection and therefore require retained gateway receipt state on every historical forwarding path? If measured, report that result as a bounded compatibility/recovery constraint within #18; keep active cancellation/side-effect resume in #20 separate. No production frontend or supervisor topology choice follows from this note.
