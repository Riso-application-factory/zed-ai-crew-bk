## Decision completeness versus delivery readiness

The mechanism choices now have named Interfaces, owners, source paths, state transitions/failure behavior, alternatives and bounded evidence. #67 answers the former current-host process-custody uncertainty; no OS/entitlement/VM change is selected. There is no remaining Human product choice identified by this architecture question: confirmed placement/storage/role/authority/US/UX choices remain, and internal technical choices are explicitly attributed as such.

The architecture does **not** promise that an arbitrary configured native/toolchain/profile is admitted before its real source/capability/data/floor checks. Runtime inputs must be explicit and validated. A failed qualification is a delivery blocker, and an exact unsupported underlying interface found during implementation reopens the related decision; it is not repaired by wider rights, fewer scenarios, pretending a skip passed or returning to a rejected shortcut.

Default SOUL wording can receive ordinary source/content review; it is not a concealed mandatory Human approval gate for architecture. No real account/profile/target-project setup or permission has been fabricated. Release/migration/incident authority remains per-project. Resource and quarantine failures remain truthful state and quality obligations, never automatic exceptions to the confirmed requirements.
